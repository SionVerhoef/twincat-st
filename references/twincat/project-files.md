# TwinCAT Project Files and Version Control

How to edit a real TwinCAT 3 (4024) project from outside the IDE without corrupting it. **TwinCAT-specific** — none of this applies to CODESYS, which uses a `.project` container instead (see `../codesys.md`).

> **Reading versus writing are different problems.** If you are *parsing* a project — extracting ST
> for context, counting POUs, mining a sample — the things to know are that `.tszip`/`.tpzip` are
> plain ZIPs (unzip twice for an InfoSys download), `.library` is compiled and has no readable
> source, and methods and properties nest *inside* the POU so a top-level-only parse drops most of
> the code. This file covers *writing* these files safely, which is the harder half.

## The parsing trap, and why it matters when writing too

Methods and properties are **nested inside** the POU, each with its own `Declaration` and `Implementation`. A naive "read the top-level `<ST>` block" grabs only the FB body and silently drops every method — the bulk of the logic in OOP code.

Measured on Beckhoff's sorting-system sample: 21 `.TcPOU` files contain **131** declaration/implementation pairs, so a top-level-only parse loses 110 of them — about **84% of the code**.

The same trap applies to writing. `scripts/tcpou.py` addresses both: it enumerates every nested part (`decl`, `impl`, `Reset:impl`, `ActualValue.Get:impl`, …) and edits them in place. `tcpou.py show <file>` is the quickest way to confirm you are seeing all of a file's code.

## The five things a write must preserve

What matters when *modifying* a file:

1. **Source lives inside `<![CDATA[ ]]>`.** Source containing `]]>` would terminate the block early — it cannot occur in valid ST, but never emit it.
2. **`Id="{GUID}"` is identity.** TwinCAT tracks objects by GUID and uses them for references. Preserve them on edit; generate a fresh one only for a genuinely new object. **Copying a template duplicates its GUID** — that is the most likely way to corrupt a project from the shell.
3. **Encoding is UTF-8 with a BOM; line endings vary.** Across 2,839 object files from the reference corpus, 97% carry a BOM but only 19% use CRLF — XAE writes CRLF, git normalisation turns it to LF, and TwinCAT reads either. The convention is usually consistent within a repository and differs between them. The rule is therefore **preserve, not normalise**: match whatever the file already uses, or a one-line edit becomes a whole-file diff.
4. **`<LineIds>` is online-change bookkeeping**, regenerated by the IDE. It churns constantly in git. Safe to ignore when reading; dropping it on a rewrite produces a noisy diff. Do not hand-maintain it.
5. **`ProductVersion`** records the build that last saved the file — useful for confirming you are on 4024.

`scripts/tcpou.py` preserves all five, and refuses the `]]>` case outright. Use it rather than hand-editing the XML.

## The silent failure: `.plcproj` registration

**A `.TcPOU` on disk that is not listed in `.plcproj` is not compiled — with no error.** The IDE adds the entry when you create a file through it; a file created from the shell will not have one.

```xml
<ItemGroup>
  <Compile Include="POUs\FB_Pump.TcPOU">
    <SubType>Code</SubType>
  </Compile>
</ItemGroup>
```

`scripts/tcpou.py register <plcproj> <file>` does this. Always run it after creating a POU/DUT/GVL from outside the IDE, and if code "isn't running", check this first.

## Library references

Also in `.plcproj`. Never reference a library that is not listed here — it will not resolve on the user's machine.

```xml
<PlaceholderReference Include="Tc2_Standard">
  <DefaultResolution>Tc2_Standard, * (Beckhoff Automation GmbH)</DefaultResolution>
  <Namespace>Tc2_Standard</Namespace>
</PlaceholderReference>
```

A `*` resolution takes whatever is installed; a pinned version is reproducible. If a project pins versions, respect that — do not "upgrade" it as a side effect.

## Version control

### `.gitattributes`

```gitattributes
*.TcPOU     text eol=crlf
*.TcDUT     text eol=crlf
*.TcGVL     text eol=crlf
*.TcTTO     text eol=crlf
*.plcproj   text eol=crlf
*.tsproj    text eol=crlf
*.xti       text eol=crlf
```

### Living with merges

TwinCAT XML merges badly. What actually helps:

- **Externalize `.tsproj` subtrees into `.xti` files.** A monolithic `.tsproj` conflicts on every I/O or task change; split files conflict only when two people touch the same device.
- **One POU per commit where you can.** Small blast radius beats clever conflict resolution.
- **Resolve conflicts inside the CDATA**, as ST — the surrounding XML is usually identical on both sides.
- **`<LineIds>` conflicts: take either side.** The content is meaningless outside the IDE, and TwinCAT regenerates it on the next save. Do not spend time merging it.
- **Never merge a conflict in `Id="{GUID}"`.** If two branches genuinely assigned different GUIDs to the same object, keep the one from the branch that has been on a machine, and open the project in the IDE to confirm before committing.
- After any non-trivial merge, **open the project in TwinCAT and rebuild** before trusting it. A file that is valid XML can still be an invalid project.
